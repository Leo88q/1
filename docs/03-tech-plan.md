# 03. Технический план: Android + Solana, без лишних сущностей

## 1. Выбор стека (решение)

Исходный план предполагал «форк C++/SDL + Solana.Unity-SDK». Это само по себе несшиваемо: `Solana.Unity-SDK` живёт внутри Unity, к C++-сборке его не подключить. Значит, развилка:

| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| **Unity 6 + Solana.Unity-SDK (MagicBlock)** | Mobile Wallet Adapter из коробки (на Android автоматически `SolanaMobileWalletAdapter`), тестовый сценарий, шейдеры/частицы, быстрый UI, один код на iOS/Android | размер билда ~60–120 МБ, лицензия Unity | ⭐ рекомендуется |
| Нативный Kotlin + `mobile-wallet-adapter-clientlib-ktx` | маленький APK, «родной» Seeker-опыт, дешевле по батарее | всё руками: рендер, UI, аналитика, IAP; веб3-часть тоже руками | хорошо, если есть сильный Android-дев |
| Godot 4 + сторонний Solana-плагин | лёгкий, открытый | MWA-интеграция слабее и менее поддерживаема | только если команда уже в Godot |
| C++/SDL (форк PipeWalker) | «как в исходном плане» | недели на тулчейн/тач/рендер, Web3 некуда прикрутить | ✗ |

**РЕШЕНИЕ ПРИНЯТО: Kotlin + Jetpack Compose (нативно), сервер на TypeScript, ядро в двух портах (TS-канон + Kotlin) со общими тест-векторами.**

Почему не Unity (хотя по таблице он был рекомендован как «быстрее всего к релизу»): Unity Editor нельзя запустить в облачной среде разработки, поэтому весь проект упёрся бы в машину разработчика; MWA в Unity SDK — обёртка, а не референс; APK в 5–10 раз тяжелее. Kotlin даёт референсный MWA, минимальный APK, полный контроль над рендером и возможность собирать подписанный APK в GitHub Actions.

Устройство репозитория (монорепо):

| Путь | Что там |
|---|---|
| `packages/engine` | Каноническое ядро правил (TS): ГПСЧ, тайлы, генератор кварталов, проверка пломбы, подсказки, тест-векторы |
| `packages/lab` | Играбельная веб-лаборатория (Vite) для проверки правил, ритма и визуального языка |
| `app-android` (следующий шаг) | Kotlin + Compose приложение, MWA, клейм cNFT; сборка APK в CI |
| `server` (следующий шаг) | challenge/verify/daily/claim, минт cNFT через Umi + Bubblegum |
| `.github/workflows` | CI: тесты ядра, typecheck, сборка подписанного APK |

Синхронизация двух портов ядра: `npm run vectors` генерирует `packages/engine/vectors/levels.json` (75 уровней + контрольные daily-seed'ы). Kotlin-тесты прогоняют те же seed'ы и обязаны получить те же маски/повороты/план ходов. Любое изменение правил = инкремент `ENGINE_VERSION` и регенерация векторов, иначе игровые daily-уровни разъедутся с серверной проверкой.

## 2. Архитектура

```
┌──────────── Android / Seeker ─────────────┐
│  UI / Presenter (Jetpack Compose, неон)   │
│  Game Core (Kotlin): grid, tiles, rotate,  │
│    solve-check, move counter, determinism  │
│  Progression: уровень, стрик, сезон        │  (локально, офлайн)
│  Wallet Module: MWA connect / signMessage  │
│  Crypto Module: challenge, claim, DAS-read │
└───────────────┬───────────────────────────┘
                │ HTTPS (REST) + RPC
┌───────────────▼───────────────────────────┐
│  Backend (Cloudflare Workers / Vercel +    │
│  Postgres):                               │
│   /challenge  — nonce для кошелька        │
│   /verify     — проверка подписи          │
│   /progress   — приём решения уровня      │
│   /claim      — выдача cNFT/скина         │
│   /daily      — seed дня, лидерборд        │
│   Indexer: Helius DAS API (чтение cNFT)    │
│   Minter: keypair в KMS, только сервер     │
└───────────────┬───────────────────────────┘
                │ devnet → mainnet-beta
        Bubblegum (cNFT) · Metaplex Core (скины)
```

### Жёсткие принципы
1. **Ключи — только на сервере** (KMS/секреты), никогда в APK. Клиент лишь просит подпись инициировать клейм.
2. **Минтит сервер**, игрок только подписывает `signMessage` (proof of ownership кошелька). Никаких «клиент сам собрал минт» — иначе спам-ферма на ваш SOL.
3. **Игра работает офлайн.** Кошелёк нужен только в момент клейма; сетевые ошибки не блокируют геймплей.
4. **Детерминированное ядро.** Уровень = seed → генерация → проверка решения. Один и тот же seed даёт один уровень на сервере и в клиенте, поэтому решение можно верифицировать на сервере.
5. **Никакого своего on-chain кода на старте.** Bubblegum + Metaplex Core покрывают 100 % нужд; свою программу пишем только когда появится реальная причина (например, турникет-скоринг).

## 3. Алгоритм ядра (то, что нужно написать)

1. Для уровня N берём seed (см. §4), детерминированно генерируем **связный остов** — дерево путей из «ячеек-проводников», покрывающее все узлы (DFS с ограничением ветвления; для сетки 5×5–8×8 — миллисекунды).
2. Из остова строим набор тайлов: углы `└┘┌┐`, прямые `─│`, тройники `┬`, кресты `┼`, источник `(S)`, узлы `(E)`; тупиков не бывает.
3. Стартовое состояние = каждый тайл повёрнут на случайный угол, кратно 90°.
4. Проверка решения: BFS от источника по совпадению «выходов» обоих тайлов; победа, когда все узлы достигнуты и все тайлы участвуют.
5. Метрики уровня: `moves`, `time`, `min_moves_estimate` (для звёзд 1–3), «без подсказок».
6. Сложность: сетка (4×4 → 8×8), плотность тройников/крестов, число источников (в поздних уровнях — два источника), число «мусорных» тайлов-отвлекателей.

Тесты: юнит-тесты на генерацию (у каждого уровня ровно одно решение из стартового состояния не требуется, но проверяем, что решение существует и начальное состояние не решено), на детерминизм (seed → идентичный уровень), на производительность (<10 мс на генерацию 8×8).

## 4. Ежедневный челлендж и лидерборды

- **Seed дня** = хэш от `sha256(slot_time_line || unix_day)`. Публикуем в `/daily`, клиент генерирует уровень сам, офлайн-играбельно; сервер принимает результат с подписью (`signMessage` от кошелька) и пишет в лидерборд.
- Подпись подтверждает «этот кошелёк заявил результат», **но не честность игры** — так и пишем в сторе. Для честности: сервер хранит стартовое состояние уровня, клиент присылает **последовательность поворотов**, сервер проигрывает её ядром и сверяет результат. Ядро существует в двух портах: **TS — канон** (серверная и CI-проверка) и **Kotlin — игровой клиент**; синхронность держится общими тест-векторами `packages/engine/vectors/levels.json`.

## 5. NFT-слой: cNFT vs Core

| Что | Стандарт | Почему |
|---|---|---|
| Массовые награды (скины, крылья, страницы лора, достижения, сезонные бейджи) | **Compressed NFT (Bubblegum)** | ~$0.00005–0.0002 за минт в дереве на миллион листьев; лимит по количеству ≈ миллионы |
| Премиум-предметы, лимитированные дропы, «предмет с уникальной логикой» | **Metaplex Core** (или обычный Token Metadata) | проще торговать, поддерживают атрибуты/плагины; дороже — только для ограниченного тиража |

Практика по cNFT:
- Дерево создаётся один раз (например, depth 17–20 → 131k–1M листьев). Оценка стоимости: ~8.5 SOL за дерево на 1 млн листьев (это оценка комьюнити по состоянию 2023–2024 — пересчитайте перед мейннетом, стоимость зависит от размера аккаунта дерева и rent).
- Коллекции: Metaplex Core Collection для группировки, MPL-Collection / verified collection внутри метаданных cNFT.
- **Читать** cNFT надо через индексер (Helius DAS API / `getAssetsByOwner`) + свою БД. RPC «сам по себе» характеристики cNFT не отдаёт.
- **Роялти в cNFT не исполняются** так, как в обычных NFT. Вывод: продавайте скины **в своей витрине** (внутриигровой магазин за $/токен), а не рассчитывайте на вторичный рынок.
- Реальная экономика: стоимость минта ≠ стоимость транзакции для игрока. **Игрок платит 0**, все комиссии и acct-rent берёт на себя проект (это часть стоимости привлечения).

## 6. Кошелёк

- `com.solanamobile:mobile-wallet-adapter-clientlib-ktx:2.2.0` (Mobile Wallet Adapter 2.x) → поддерживаются Seed Vault Wallet на Seeker, Phantom, Solflare, Backpack и любые MWA-совместимые.
- Кода под конкретный кошелёк нет: MWA-сессия запускает системный выбор кошелька, поэтому **Phantom и Seed Vault покрываются одним флоу**. Отличия (SIWS-подпись, поведение connect) проверяются на устройстве: Seed Vault на Seeker, Phantom — из Play Store.
- Подпись клейма — `signMessagesDetached(nonce)`: транзакций от игрока нет, каждая транзакция = комиссия проекта, их минимум.
- Первый вход: играем без кошелька → баннер награды → connect → `signMessage(challenge)` → сервер минтит cNFT → клиент показывает клейм. Никаких транзакций от игрока.
- Безопасность: храните только публичный ключ, авторизационные токены — в памяти, отключите Android backup для данных приложения.

## 7. APK и публикация в dApp Store

1. Собрать **APK** (не AAB), подписать **отдельным ключом** (ключ Google Play не подойдёт). Ключ хранить в менеджере секретов, не в репозитории. Сборка идёт в GitHub Actions (`.github/workflows/android.yml`): debug-APK — всегда, release-APK — при наличии секретов `AMPERGRAD_KEYSTORE_B64/_PASSWORD/_ALIAS/_KEY_PASSWORD`. Артефакты: `ampergrad-apk`.
2. Package id — свой бренд: `game.<studio>.<title>`.
3. Регистрация на `publish.solanamobile.com`, KYC/KYB (для физлица — паспорт/селфи; для юрлица — документы компании).
4. Подключить publisher wallet (Phantom/Solflare/Backpack) и пополнить **~0.2 SOL** на комиссии + ArDrive.
5. Storage provider: **ArDrive** (рекомендован, дешевле); оценить стоимость через их storage cost tool — она зависит от размера APK + ассетов.
6. Выбрать категорию (Puzzle), загрузить иконку, скриншоты, фичер-график, видео, описание, privacy policy.
7. «New Version» → загрузка APK → подписать все запросы (каждый минтит/обновляет on-chain объект). Пропущенная подпись = потерянные ассеты.
8. **Ревью 3–5 рабочих дней.** Финансовые/призовые механики и NFT разрешены Publisher Policy, но опишите их в листинге честно.
9. Обновления — быстрее через CLI (`@solana-mobile/dapp-store-cli`) с API-ключом из настроек портала: минтится только новый Release NFT.

Материалы для сабмита лежат в `store/`: тексты листинга (`listing.md`, `listing.en.md`), политика конфиденциальности (`privacy.md`), ассеты (иконка, фичер-график, скриншоты — рисуются по кадрам движка) и пошаговый чек-лист (`checklist.md`) с разделением «сделано в репозитории / нужно владельцу».
